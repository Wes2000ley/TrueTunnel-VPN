# TrueTunnel security design

This document describes the security properties of TrueTunnel
3.1.0-preview.1. The last stable tag is V3 (3.0.0). It is a design record,
not an independent audit or a certification. The complete VPN
protocol is younger and less widely reviewed than WireGuard or IKEv2/IPsec.

## Security profiles

| Transport | Required profile | Authentication |
| --- | --- | --- |
| TCP | Windows Schannel TLS 1.3, `TLS_AES_256_GCM_SHA384` | Exporter-bound proof of the 256-bit group key |
| UDP | wolfSSL DTLS 1.3, `TLS_AES_256_GCM_SHA384`, P-256 ECDHE | External PSK binder derived from the 256-bit group key |

Older TLS versions, alternate UDP ciphers, RSA/finite-field DH, AES-CBC,
ChaCha20-Poly1305, session tickets, and the former custom UDP cryptography are
not part of the active profile. OpenSSL is not linked or required. UDP uses
wolfSSL's user-mode DTLS implementation; wolfGuard is a Linux kernel module and
is not used by the Windows product.

## Authentication and key handling

The GUI creates a uniformly random 256-bit shared key with the Windows CNG
system CSPRNG. Its encoding is 43 unpadded base64url characters. The desktop
shows only a masked placeholder; native clipboard controls transfer the value.
The key never enters JavaScript, JSON, the DOM, or browser storage. Inputs are
validated for the canonical encoding before socket, certificate, KDF, or Wintun
work. Server mode accepts only a key generated by the application; client mode
uses the copied server value. The key is not persisted, and clipboard sharing
opts out of clipboard history/cloud synchronization and is cleared after a
bounded interval while ownership is still verified.

TCP obtains 32 bytes from the Schannel TLS exporter. Each side contributes an
independent 32-byte nonce, derives an authentication key with PBKDF2-HMAC-SHA-
256 (100,000 iterations), and exchanges role-separated constant-time HMAC
proofs. The proof binds the shared key, exporter, nonces, role, and required
cipher, so a valid TLS channel with the wrong group key is rejected.

The server's ECDSA P-384 certificate is transient and non-exportable. It
provides the Schannel server signature but is not installed into a certificate
store and is not treated as hostname/CA identity. The shared-key proof is the
peer authentication mechanism.

UDP derives a 32-byte external PSK with PBKDF2-HMAC-SHA-256 (200,000
iterations) and a protocol-specific salt. TLS 1.3 DHE-PSK with P-256 is
mandatory, providing forward secrecy per handshake. Stateless cookies are
bound to the complete peer socket address and use an hourly rotated CNG secret;
the TLS PSK binder is verified before a stateful peer queue or worker is
allocated.

Temporary exporter bytes, proofs, derived keys, decrypted buffers, and shared
key copies are explicitly cleared. Optional recovery keeps one additional
in-memory key copy and attempts page locking when Windows permits; an
administrator, debugger, or process compromise can still inspect live secrets.

## Rekey and renewal

UDP requests a DTLS 1.3 traffic-key update before one million records, 1 GiB of
application data, or one hour in one traffic-key epoch. A failed update closes
the secure connection.

Schannel does not expose a supported application-triggered TLS 1.3 `KeyUpdate`
operation. TCP therefore performs a complete make-before-break TLS renewal with
fresh handshake traffic keys before one million records, 1 GiB, or one hour.
The trigger uses the greater of 20% policy headroom or fixed reserves sized to
complete the handoff safely. The authenticated transaction is:

```text
OLD: FREEZE -> FREEZE_ACK
NEW: authenticate -> PREP_ACK -> DRAIN/BARRIER -> READY
cutover: ACTIVATE -> COMMIT -> COMMIT_ACK
```

The binding covers both OLD and NEW TLS exporters, a fresh nonce, and the
assigned tunnel IP. Application writes pause only for a bounded handoff window.
Before `ACTIVATE`, failures authenticate an abort and resume OLD. After
`ACTIVATE`, any ambiguity closes both generations; the client may use optional
recovery to establish fresh keys. The old continuity binding is erased on
success.

This is session renewal, not an undocumented Schannel KeyUpdate and not a
guarantee of uninterrupted service across an arbitrary network failure.

## Record, resource, and input bounds

- IPv4 packet payloads are capped at the 1380-byte Wintun MTU; UDP datagrams are
  capped at 1472 bytes.
- Every frame checks type, length, IPv4 version/header/total length, source
  address, and prospective record/byte counters with overflow-safe arithmetic.
- Partial application-frame reads and possibly partial encrypted writes make a
  stream terminal; there is no attacker-controlled resynchronization path.
- TCP accepts, UDP stateless/stateful handshakes, tracked peers, peer queues,
  chat, fanout, sources, and per-operation deadlines are independently bounded.
- A stalled writer cannot pin a worker forever; shutdown cancels blocked reads
  and writes before joining worker threads.
- An authenticated client can inject only the IPv4 source address assigned to
  it. IPv6 is rejected because the product is IPv4-only.

## Windows and device boundary

`wintun.dll` is loaded from the executable directory by absolute path, checked
for reparse/hard-link substitution, hashed while held open, and compared with
the pinned SHA-256 in the build and loader. The application should still be
installed in an administrator-writable, standard-user-read-only directory.

The Wintun adapter uses a deterministic GUID and a named interprocess lease.
Alias owner, Wintun name, GUID, LUID, routes, firewall rule, and IP rows are
matched exactly. Foreign adapters are never renamed or deleted by prefix. This
protects unrelated Windows networking state and avoids numbered TrueTunnel
aliases after a crash.

The server firewall rule is temporary, executable-scoped, and restricted to the
selected protocol/address/port. Optional RRAS NAT commands use absolute
`System32\netsh.exe`, bounded execution, and ownership-aware cleanup. RRAS is
not required for authenticated peer-to-peer tunnel traffic.

## Threat model and limitations

The design protects tunnel confidentiality and integrity against a network
attacker who does not possess the shared key. It does not provide a PAKE:
captured UDP binders can test password guesses, which is why human passwords
are rejected and a CSPRNG-generated key is required.

The shared key is a group credential. There is no per-device identity,
individual revocation, authorization policy, or attribution. Rotate it when a
member leaves or exposure is suspected. The TCP certificate is not hostname-
validated. Recovery does not add roaming, packet preservation, or per-peer
identity. There is no IPv6 policy, DNS-leak policy, kill switch, signed updater,
or FIPS validation. The GUI is now unelevated, with a separate on-demand elevated
worker, not a persistent hardened Windows service. The WebView2 engine adds a
dependency that must receive security updates. The full desktop/IPC boundary has
not received an independent security audit.

## Desktop and privileged worker

The desktop uses embedded React assets, an InPrivate WebView2 profile, exact-origin
message validation, a restrictive CSP, and denied navigation/downloads/permissions.
No web page or development server can directly call the elevated worker.
Native clipboard handling retains the 30-second ownership-checked lease and
history/cloud exclusion hints. Page locking is best-effort, not protection against
an administrator, debugger, compromised same-user process, clipboard reader, or
memory dump. Clipboard exclusion hints cannot constrain every third-party manager.

The private named pipe rejects remote clients, restricts its DACL to the user and
administrators, and verifies the expected peer PID, image path, and user SID in both
directions. Binary frames are versioned and capped at 32 KiB; Start has one exact
size, chat is capped at 512 UTF-8 bytes, and the native worker revalidates inputs.
Only the native request carries the key; copies are wiped after transfer/use.
Loss of the UI, pipe, or protocol validity stops the existing daemon normally.
The worker retains the original TLS/DTLS, adapter ownership, firewall, recovery,
and key-renewal policies. The frontend cannot select weaker cryptography.

Same-user elevation is required. Protect the installed EXE/DLL directory; path
and PID checks are not code signing or a defense against an administrator replacing
the executable. This separation reduces browser privilege, but is not a promise
that frontend compromise or local malware is harmless.

## Comparison

WireGuard is the stronger general-purpose default: it has mature per-peer
Curve25519 identity, built-in roaming/rekey behavior, IPv6 support, and a small
purpose-built protocol. IKEv2/IPsec is generally better where native OS
clients, certificates/EAP, enterprise policy, MOBIKE, and standards
interoperability matter. TrueTunnel is a specialized Windows IPv4 VPN whose
strengths are Schannel TLS and wolfSSL DTLS choices, a Wintun dashboard,
optional TCP fallback, and an auditable bounded lifecycle in this repository.
It should not be marketed as cryptographically equivalent to either mature
alternative.
